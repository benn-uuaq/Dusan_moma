# 차량(AGV) 개발 쪽에 요청하는 값 — 캘리브레이션 한 바퀴 거리 · 배터리

작성 2026-09-30 · 3S RCS · 근거 규격: ERUT 검사로봇 MQTT 표준 인터페이스 **if-0.4**

RCS(3S)가 ERUT 에 보내야 하는 값 중 **차량만 알 수 있는 것**이 두 가지 있습니다.
지금 차량 연동 인터페이스(`vehicle_interfaces`: `RobotStatus`·`SetJob`·`RobotControl`·
`ManualCommand`)에는 이 값을 받을 자리가 없어, 아래처럼 추가를 요청드립니다.

---

## 1. 캘리브레이션 때 차량으로 한 바퀴 돈 총 거리

> **2026-10-02 ERUT 확인 — `req/calibrate` 자체가 차량(AGV) 캘리브레이션입니다.**
> 원형 모재 정보(지름·높이)를 받아 차량이 외벽을 따라 붙어 한 바퀴 돌며 맵(좌표계)을
> 그립니다. 협동로봇의 3점 측정은 캘리브레이션이 아니라 구간 검사(start) 시작 때 합니다.
> 그래서 아래 "한 바퀴 측정"은 부가 기능이 아니라 **캘리브레이션의 본체**입니다.
> 그때까지 RCS 는 차량에 "둘레(π × 지름)만큼 이동"을 시키고 달린 거리(위치 변화)를
> `total_length_mm` 로 보내는 임시 방식으로 돕니다.

### 왜 필요한가

ERUT 는 캘리브레이션이 끝나면 `total_length_mm` 를 받아 **계획 둘레(π × 지름)와
견줍니다.** 크게 다르면 다른 모재이거나 원점 기준이 옮겨진 것으로 보고 검사를
세웁니다(규격 탭3 8번). 이 값은 협동로봇이 아니라 **차량이 모재를 한 바퀴 돌면서
잰 거리**입니다.

### 요청하는 동작

1. RCS 가 "한 바퀴 측정 시작"을 보낸다.
2. 차량이 **캘리브레이션 원점(시작 지점)에서 출발해 모재를 한 바퀴 돌고, 원점에
   돌아오면 선다.** 원점을 어떻게 다시 알아보는지(QR 표식 등)는 차량 쪽 방식대로.
3. 차량이 **실제로 달린 경로 길이**와 **도는 동안 모재 표면까지의 거리**를 알려 준다.
4. RCS 가 경로 길이를 모재 표면 둘레로 바꿔 ERUT 에 보낸다.

> 차량은 모재에서 떨어진 원을 돌기 때문에 경로 길이는 모재 둘레보다 깁니다.
> 모재 표면까지의 평균 거리 d 를 같이 주시면 RCS 가
> **모재 둘레 = 경로 길이 − 2π·d** 로 계산합니다(동심원 기준).
> 차량 쪽에서 모재 둘레로 바꿔 줄 수 있으면 그 값을 주셔도 됩니다 — 어느 쪽인지만 알려 주세요.

### 인터페이스 제안 (둘 중 편한 쪽)

**안 A — 서비스 하나 추가 (권장)**

```
# vehicle_interfaces/srv/MeasureLap.srv
# Request
string  job_id        # RCS 가 정한다. 예: "CAL-20260930-01"
float64 speed         # 목표 속도 [m/s]. 0 이면 차량 기본값
---
# Response
bool    success       # 측정을 시작했는가
string  message       # 거절 사유 (예: "Rejected: outrigger set")
```

결과는 `RobotStatus` 에 칸을 더해 받습니다.

```
# RobotStatus.msg 에 추가
string  lap_state          # "IDLE" / "RUNNING" / "DONE" / "FAILED"
float64 lap_path_m         # 한 바퀴 동안 달린 경로 길이 [m] (DONE 일 때 확정값)
float64 lap_wall_dist_m    # 도는 동안 모재 표면까지의 평균 거리 [m]
string  lap_error          # FAILED 일 때 사유 (예: "origin marker not found")
```

**안 B — 기존 `SetJob` 재사용**

`job_id` 앞머리가 `CAL-LAP` 이면 "원점으로 돌아올 때까지 한 바퀴"로 해석하고
(`set_dist` 는 무시하거나 안전 상한으로 사용), 끝나면 `state = "STOP"`,
`mv_dist` = 경로 길이로 두는 방식입니다. 이 경우에도 모재까지의 거리
(`sen1_dist`·`sen2_dist` 중 어느 것이 모재 표면 거리인지, 단위·설치 위치)를 알려 주세요.

### 함께 알려 주셨으면 하는 것

| 항목 | 이유 |
|---|---|
| 한 바퀴 거리의 반복 정밀도 (같은 모재를 여러 번 돌 때 편차) | ERUT 가 "계획 둘레와 크게 다름"을 판단할 기준이 된다 |
| 원점 인식 방법과 정지 위치 오차 | 원점에서 선 자리가 곧 격자 1A 자리다 |
| 한 바퀴 측정에 걸리는 시간 (최대값) | ERUT 가 캘리브레이션 완료를 얼마나 기다릴지 정한다(기본 5분) |
| 측정 중 아웃트리거·리프트 상태 조건 | 아웃트리거가 고정된 상태에서는 달릴 수 없으므로 RCS 가 먼저 풀어야 하는지 |
| 실패하는 경우와 그때 주는 사유 | RCS 가 ERUT 에 5xx 로 실패를 알려야 한다 |

## 2. 배터리 잔량 · 충전 상태

### 왜 필요한가

ERUT 는 구간을 시작하기 전과 구간 완료 때마다 배터리를 보고 **다음 구간을 할지**
정합니다(최소 배터리 미만이면 일시정지 → 충전 뒤 재개). 규격은 배터리가 없는
장비는 칸을 **아예 빼라**고 합니다 — 0 으로 채우면 전선으로 전기를 받는 장비가
영영 시작을 못 하기 때문입니다. 그래서 지금 RCS 는 배터리 칸을 보내지 않고 있습니다.

### 요청

```
# RobotStatus.msg 에 추가
uint8   battery_pct     # 잔량 0~100 [%] 정수. 모르면 255
bool    charging        # 충전 중이면 true
```

- **정수**로 주세요(if-0.4 에서 "0~100 정수, 소수 금지"로 못 박혔습니다).
- `RobotStatus` 를 내는 주기 그대로 같이 실어 주시면 됩니다(1 Hz 이상).
- 차량이 유선 급전이라 배터리가 없는 구성이면 `battery_pct = 255` 로 고정해 주세요.
  RCS 는 255 를 보면 ERUT 에 배터리 칸을 싣지 않습니다.
- 충전 스테이션으로 스스로 가는 기능이 있는지도 알려 주세요. 자리를 떴다 오면
  RCS 가 ERUT 에 "좌표계 무효"(E1003)를 알려야 합니다.

## 3. RCS 가 이 값을 어디에 쓰는가 (참고)

| 차량 값 | RCS → ERUT |
|---|---|
| 한 바퀴 경로 길이 · 모재까지 거리 | `evt/complete(action=calibrate).total_length_mm` (정수 mm) |
| `battery_pct` | `evt/status.battery` · `res(query).battery` · `evt/complete(action=start).battery` (정수 %) |
| `charging` | `evt/status.charging` · `res(query).charging` |
| 자리 이탈(충전 이동 등) | `evt/error` E1003 CALIBRATION_LOST · `calibrated=false` |

값이 오기 전까지 RCS 는 이 칸들을 비워 두고, ERUT 에 보내는 자기소개(`evt/info`)의
기능 목록에서도 `battery`·`charging` 을 빼 두었습니다. 받는 대로 넣겠습니다.
