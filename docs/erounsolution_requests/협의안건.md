# MQTT 인터페이스 협의 안건

다 확정하기보다는 **방향을 맞추고 남은 확인 사항을 나누는 것**이 목표입니다.  
아래 내용은 모두 저희 초안이니 편하게 의견 주시면 감사하겠습니다.

---

## 안건

| \# | 안건 | 논의하고 싶은 것 |
| :---: | :---- | :---- |
| 1 | 인터페이스 방식을 요청/응답 구조 변환 | 이 방향으로 가도 될지 아니면 일부만 적용 |
| 2 | 토픽·동작 구성 초안 | 초안 검토, 수정 의견 |
| 3 | 응답 공통 규칙 | req\_id 회신 · 중복 처리 · code 형식 |
| 4 | 스테이션 끊김 시 로봇 동작 | 작업 중 자동 일시정지가 가능한지 |
| 5 | 안전 신호 경로 | MQTT 밖 하드와이어 구성 확인 |

## 안건 1\. 인터페이스 방식: 요청/응답 구조

**배경** : 현행 규격(주기 상태 발행)으로 저희가 어려움을 느끼는 부분이 있습니다.

- 명령을 보내고 나서 수락됐는지, 거절됐는지, 이유가 무엇인지에 따라 다시 요청 해야 하는데 이런 부분을 최소화 하고자 합니다.  
- 상태값 여러 개를 조합해 저희가 해석해야 해서, 해석이 어긋나면 오동작으로 이어질 우려가 있습니다.

**제안 방향** : 필요할 때 요청을 보내고 로봇이 결과를 답해주는 방식입니다.  
예) 검사 준비 단계

현재 :  로봇이 발행 해주는 정보를 취합 후 스테이션이 **판단**하여 검사 요청  
제안 :  "검사 준비" 요청 1번  →  로봇이 OK 또는 "배터리 부족 (18%, 최소 30%)" 회신

- HTTP API처럼 요청 → 응답으로 동작하고, 오래 걸리는 작업만 끝났을 때 완료 알림을 한 번 발행하는 형태입니다.  
- 거절 사유가 코드와 함께 오면 화면에 그대로 띄울 수 있어서 로봇이 정의한 오류를 바로 보여줄 수 있습니다.

## 안건 2\. 토픽·동작 구성 (초안)

### 토픽 7개

| 토픽 | 역할 | 보내는 쪽 |
| :---- | :---- | :---- |
| `/robot/req/{동작}` | 요청 | 스테이션 → 로봇 |
| `erut/evt/ready` | 준비 완료 알림 | 로봇 → 스테이션 |
| `erut/evt/complete` | 오래 걸리는 작업의 완료 알림 | 로봇 → 스테이션 |
| `erut/evt/error` | 장애 알림 | 로봇 → 스테이션 |
| `erut/status` | 스테이션 접속 상태 · retained \+ LWT | 로봇 → 스테이션 |

접속 상태는 양방향으로 두어 서로의 끊김을 알 수 있게 하는 안입니다 (용도는 안건 4).

### 동작 6개

모두 스테이션이 요청하고 로봇이 응답하는 구조입니다. 로봇 기준으로 req는 구독, res·evt는 발행입니다.

| 동작 | 하는 일 | 응답 방식 |
| :---- | :---- | :---- |
| `calibrate` | 모재 크기로 원점 잡기 | 완료 알림 발행 |
| `prepare` | 검사 준비 (면·영역·스캔 조건) | 완료 알림 발행 · 배터리 부족 등 거절 사유는 여기서 회신 |
| `start` | 검사 시작 | 완료 알림이 곧 "검사 끝" 신호 |
| `pause` / `resume` / `abort` | 일시정지 / 재개 / 중단 | 즉시 응답으로 끝 |
| `mark` | 지정 좌표로 이동해 마킹 | 완료 알림 발행 · 좌표 이동 기능 겸함 |
| `query` | 현재 상태 조회 | 즉시 응답 · 재접속 후 동기화용 |

### 받은 메시지를 스테이션 처리 방안

| 로봇이 발행 | 스테이션의 반응 |
| :---- | :---- |
| `evt/fault` | 화면에 알림 표시, 심각도에 따라 검사 중단 |
| `status` | 화면에 알림 표시, 설정에 따라 검사 중단 |
| `evt/progress` | 진행 화면에 표시 |

**논의하고 싶은 점** : 토픽 이름, 동작 구성 모두 초안입니다. 로봇 쪽 구현 관점에서 다듬을 부분이 있으면 알려주시면 좋을거 같습니다.   
타임아웃 값 같은 세부 설정은 저희 쪽에서 쉽게 조정할 수 있으니 나중에 바꿔도 됩니다.

## 안건 3\. 응답 공통 규칙 (안)

아래 3가지는 값이 아니라 동작이라서 처음부터 맞춰야 하는 부분이라, 이유와 함께 가져왔습니다.

1. **응답에 요청의 `req_id`를 그대로 담기** : 어느 요청의 답인지 구분하기 위해서입니다.  
2. **같은 `req_id`가 두 번 오면 재실행하지 않고 이전 답을 다시 발행** : 통신이 불안정할 때 저희가 재전송을 하는데, 이 규칙이 없으면 검사나 마킹이 중복 실행될 수 있습니다.  
3. **응답 형식을 `code` / `message` / `content`로 통일** : 일단 감싸는 방법은 이렇게 하려고 합니다.  
   안에 code 정의나 메시지 컨텐츠는 로직상 필요한 값으로 사용할 정보들을 담아주시면 좋을듯 합니다.

**논의하고 싶은 점** : 2번(중복 처리)은 최근 `req_id` 일부만 기억하면 되는 수준으로 생각하고 있습니다.

## 안건 4\. 스테이션 끊김 시 로봇 동작

**배경** : 스테이션(ERUT)은 노트북에서 돌아갑니다. 전원이 꺼지거나, 오류로 종료 되거나, wifi가 끊길 수 있습니다. 그 사이 검사가 계속되면 데이터를 받는 쪽이 없어서 의미 없는 검사가 됩니다.

**제안** : 로봇이 `erut/status`를 구독하고 있다가, **작업(검사·마킹) 중에 `offline`이 되면 진행 중인 작업을 자동 일시정지**하는 안입니다.

- 비상정지가 아니라 **일시정지**입니다. (위치를 유지한 채 멈추면 됩니다.)  
- 스테이션이 복귀하면 `query`로 상태를 확인한 뒤 `resume`으로 이어갑니다.

## 안건 5\. 안전 신호 경로 (MQTT 밖)

MQTT로 처리가 아닌걸로 알고 있는데 구성 방향을 확인하고 싶습니다.

- `abort`·`ems`는 네트워크 명령이라 안전정격 비상정지로 보기는 어려울 것 같습니다. 물리 E-stop 버튼과 안전 릴레이를 별도로 두는 구성이 맞을지요.  
- 안전센서(레이더·LiDAR)의 정지 신호는 로봇과 스테이션에 어떤식으로 신호를 줄 수 있는지 확인이 필요합니다.
